# 多版本兼容开发规范

## 1. 适用范围与目标

- 术语约定: 文中以"平台"统称模组加载器侧的 API 体系与构建体系, 以"原版"统称 Minecraft 自身
- 规定"新增一个受支持的 Minecraft 版本区间或平台版本区间"时必须走的流程, 以及过程中必须遵守的约束
- 规定多版本产物的组织方式, 命名方式, 构建方式与登记方式
- 适用于任意模组加载器: 规则不得绑定任何具体加载器的接入点; 当前仓库的落地实例是平台 = Forge 一侧, 将来增加其他加载器时只需替换平台接入点, 流程与规则不变
- 不描述单个功能的具体实现

## 2. 术语

| 术语 | 含义 |
|:---:|:---:|
| 基线 | 唯一的功能真源源码, 当前为 `src/main` 与工作目录根目录的构建脚本 |
| 目标 | 一段连续受支持的 MC 版本区间, 及其配套的平台版本区间 |
| 目标标识 | 目标的唯一名字, 同时用作目标目录名与产物名前缀后缀 |
| 补丁层 | 一个目标相对基线的差异集合, 以整文件覆盖方式表达 |
| 同名层 | 多个目标各自持有一份副本的层, 各副本内容必须一致 |
| 探针 | 为"某版本相对基线到底改了什么"而做的一次性构建, 以编译器错误定位改动面 |
| 工作副本 | 由基线与补丁层合成出的, 可直接构建的临时工程 |
| 分叉点 | 使同一份编译无法同时满足两侧的破坏性变更所在版本 |

## 3. 核心模型

多版本兼容由四件事构成, 缺一不可:

1. **基线唯一**: 功能只在基线中开发与修复, 任何目标都不允许成为新功能的开发场所, 否则功能会分叉成多份
2. **目标是声明**: 目标只描述版本区间, 平台版本, 所需语言级别, 补丁层构成等参数, 本身不是源码副本
3. **补丁层是差异**: 补丁层只承载"该目标与基线不同"的部分, 不承载基线已有的内容
4. **合成可重建**: 任一目标都必须能由"基线 + 该目标的声明"完全重建; 合成结果必须与人工手改等价

由此得到三条不变量, 任何一次变更都不得破坏:

- 基线必须能独立构建通过, 且功能完整
- 任一目标的重建不依赖任何人工临时改动
- 任何功能的修复只需在基线改一次, 即对所有目标生效, 除非该功能本身位于分叉点上

## 4. 目标划分规则

### 4.1 何时必须拆成不同目标

出现以下任一情况, 必须拆分目标:

- **平台 API 换代**: 同一接入点在新旧平台间不存在同名同义的写法
- **原版签名或类型变更**: 同一覆写点或调用点的签名, 参数类型, 返回类型发生变化
- **语言级别变更**: 目标所需的语言版本高于基线, 且无法用兼容写法回避
- **构建体系不兼容**: 平台构建插件无法在同一工程内同时建立两套版本配置

### 4.2 何时可以合并为一个区间

区间内只出现"新增 API 或兼容性扩展"时可以合并, 判定依据是实测而不是推断:

- 范围产物对准区间内**最旧**的 MC 与平台版本编译
- 若最旧版本编译通过且区间内其余版本实测通过, 则该区间成立
- 严禁反向推定: 较新的版本通常保留旧写法, 因此"对准最旧版本编译"是唯一安全的做法

### 4.3 区间的边界规则

- 一个产物只声明一个**连续**区间; 不连续的支持范围必须拆成多个产物
- 产物声明的区间必须与其内部元信息声明一致, 不允许只改文件名而留下旧区间
- 区间内每一个版本都必须实测, 区间是承诺, 不是近似

## 5. 新增版本兼容的流程

按顺序执行, 任一步不通过则回到上一步重新判定

1. **确定候选区间**: 收集该 MC 版本对应的平台版本落在哪个平台主版本段内, 以及原版是否需要更高的语言级别
2. **是否落在已有区间内**: 若是, 直接做实测验证, 通过则只需把该版本登记进已有目标的实测记录, 不新增目标
3. **定位分叉点**: 对候选区间的最旧版本做一次探针构建, 让编译器把"该版本相对基线改了什么"逐条报出
4. **归类差异**: 把报出的差异分成三类, 分别决定其归属:
   - 平台侧差异: 归入平台层
   - 原版侧差异: 归入原版层
   - 仅该区间才有的差异: 归入区间专属层
5. **写补丁层**: 按第 6 节的补丁层规范编写, 且每一层只解决一类差异
6. **声明目标**: 在 `versions/versions.json` 登记该目标的条目, 含目标标识, 标签, MC 与加载器版本数组, Gradle 与 jdk 版本, 资源包格式号; 建立 `versions/<目标标识>/` 目录并在其中写 `diff-baseline.json`, 逐文件记录该目标相对基线的差异; 需要复用的内容从 `versions/.sync/<层>/` 引用, 该目标独有的内容放该目录的 `patch/<层>/`
7. **准备与审查工作副本**: 只生成工作副本而不构建, 逐条核对合成结果是否为预期的最小差异
8. **构建**: 生成并构建, 确认产物名, 元信息声明与实际区间三者一致; 同一语言级别下已有多个目标时, 可用 `jdk-build <主版本>` 一次依次构建它们
9. **实测**: 在区间内每个版本上分别做功能实测, 覆盖该模组的主要交互路径
10. **登记结论**: 把该目标的差异清单, 实测结论与未取证项写入评估报告, 并把机制层面的结论同步进本规范或项目信息文档

### 5.1 探针机制

探针是"用编译器当探测器"的手段, 规范如下:

- 探针只用于定位改动面, 不用于产出交付产物
- 探针应当复用目标声明, 仅临时替换编译对准的 MC 与平台版本
- 探针属于临时性工作, 其工作副本必须落在临时目录下, 不得占用 `versions/` 的目标命名空间(`versions/` 下只允许出现符合命名规则的真实目标目录)
- 探针的输出是编译器错误清单, 该清单必须逐条判定归属, 不允许凭记忆或推断直接写补丁
- 探针结论必须记录"哪一条差异在某版本出现, 在哪一版本消失", 这是判断分叉点的直接依据

### 5.2 从最旧版本开始

- 一个区间只对准其最旧版本编译
- 新增区间时, 必须重新在最旧版本上做一次完整构建, 不允许沿用较新版本的构建结果
- 实测顺序建议从最旧到最新, 尽早暴露缺失的兼容层

## 6. 补丁层规范

### 6.1 表达方式

- 补丁层以**整文件覆盖**表达, 即补齐相对路径下的完整文件
- 禁止片段式补丁: 片段补丁会随基线改动静默失配, 且无法被构建直接发现
- 需要删除基线中的文件时, 在层内集中登记删除项, 不允许通过"留空文件"等方式变相删除
- 之所以必须用覆盖而不能用并列源码目录: 并列源码目录对同语言源文件会构成重复定义, 对同路径资源则是先声明者胜, 二者都没有确定性的覆盖语义

### 6.2 层内构成

- 一层只解决一类差异, 层名应当表达"该层解决哪一类差异"或"该层服务于哪个版本区间"
- 层与层之间不得出现同一文件的重叠覆盖, 除非是刻意叠加: 后者覆盖前者, 且必须在层说明中写明叠加意图
- 后置层的源必须取自其前驱层的产物, 不得取自基线: 若某层要改动前驱层已经改过的同一文件, 从基线取源会把前驱层的改动一并抹掉, 而这类问题只在真实构建时才暴露(表现为"方法不会覆盖或实现超类型的方法"等回退性错误)
- 因此新增层时应先确认: 该文件是否已被更早的层改过; 若已改过, 则在前驱层产物之上继续叠加, 而不是重新从基线出发
- 跨版本共用的补丁内容只在 `versions/.sync/<层>/` 存一份, 各目标的差异清单按 "层目录名/层内相对路径" 引用它; 目标独有的内容放 `versions/<目标标识>/patch/<层>/`
- 差异清单的 `add` 项按数组顺序生效, 同一目标文件被多条 `add` 写入时后者覆盖前者, 该情形由脚本列出以便审查
- 某个层是否引入, 取决于编译对准的那一版是否具备它所规避的 API, 与目标覆盖了哪些 MC 版本无关: 例如某个方法只在部分平台版本上缺失时, 是否引入补救层由"编译对准的版本"决定, 而不是由目标覆盖的版本集合决定
- 只服务单个目标的层放在该目标自己的目录内, 避免同类补丁在多份目标目录里重复维护

### 6.3 最小差异原则

- 补丁层与基线的差异必须最小: 只改必须改的, 不顺带格式化, 不顺带重命名, 不顺带升级写法
- 补丁层内必须用注释说明"为什么要改", 并给出取证来源; 不写"改了什么"这种代码本身已表达的信息
- 若某处差异可以用兼容写法在基线上消除, 应优先改基线, 而不是在每个目标里各写一份补丁

### 6.4 平台接入点的分歧

平台接入点是多版本兼容中最容易反复出问题的部分, 规范如下:

- 凡"注册什么""从哪个入口订阅""如何投递"这类平台接入点, 一旦在某个分叉点发生变化, 必须由平台层统一承担, 不允许在业务代码里散落版本判断
- 平台侧移除某个接入点而原版没有等价公开入口时, 允许在补丁层内引入受控的底层注入(如字节码注入)作为替代挂载点, 但必须满足: 只影响该区间, 注入点稳定, 且注入失败时功能降级而不崩溃
- 引入底层注入前必须先确认是否存在公开入口; 若存在公开入口, 禁止使用注入

### 6.5 重映射与命名

- 是否需要为目标额外声明符号重映射配置, 必须在目标构建中实测判定, 不允许凭经验假设
- 若新平台的运行时已改用与源码一致的符号命名, 则不应为其引入整套重映射链路, 可对单个注入点显式声明"不参与重映射"

## 7. 命名规范

- 目标标识与目标目录名, 产物名后缀三者同源同序, 由同一组参数推导, 不允许各自维护
- 顺序固定为"先 MC 后平台": `mc-<起始MC>_<终止MC>-<平台名>`; 平台版本号不进标识, 因为它由该目标的 MC 版本决定, 写进标识会变成第二份真源
- 某一端版本匿名时, 该位置留空但仍保留下划线, 以区分该版本号属于起始还是终止, 例如上界匿名写作 `<平台>-<起始>_`, 下界匿名写作 `mc-_<终止>`
- 不允许两端同时匿名
- 起始与终止一致时合并为单值, 不再保留下划线(如 `mc-1.20.6-forge`): 单版本目标若仍写成区间形式, 会让人误以为存在一个版本区间
- 产物名由"模组名 + 模组版本 + 目标标识"构成, 与目标目录名共用同一段标识
- 目标标识只由参数推导, 禁止手工拼接或手工改名

## 8. 目录与文件系统规范

- 共用内容只保留在工作目录根目录: 基线源码, 构建脚本, 构建包装器
- 各目标独有的内容分片放在目标目录下, 分为三部分:
  - 该目标的差异清单 `diff-baseline.json`, 纳入版本控制
  - 该目标自带的补丁内容 `patch/<层>/`, 纳入版本控制
  - 生成的工作副本 `work/`, 不纳入版本控制
- 工作副本必须与差异清单, 补丁目录分离且位于其子目录: 准备工作副本时该目录会被整体重建
- 生成物只有工作副本一处, 忽略规则用一条正面规则 `versions/*/work/` 即可覆盖, 不需要逐级否定
- 结构表达:

```
<工作目录>/
├── src/main/                        基线源码(唯一功能真源, src 下不再有别的目录)
├── versions/
│   ├── versions.json                多版本列表的唯一权威来源(人工维护, 脚本只读)
│   ├── build_version.py             多版本适配生成脚本
│   ├── .sync/<层>/                  跨版本共用的补丁内容(每层只存一份, 纳入版本控制)
│   └── <目标标识>/
│       ├── diff-baseline.json       该目标相对基线的差异清单(纳入版本控制)
│       ├── patch/<层>/              该目标独有的补丁内容(纳入版本控制)
│       └── work/                    生成的工作副本(不纳入版本控制)
└── scripts/                         素材处理等辅助脚本
```

## 9. 构建环境规范

- **语言级别随目标走**: 构建某目标前必须把当前语言级别切到该目标要求的版本; 生成脚本只做检查, 不符合时直接拒绝构建, 不做版本切换、不做兜底、不查找其他 JDK 安装路径
- **不注入工具链**: 生成脚本不写任何工具链或 home 配置; 由于当前语言级别不符合目标要求时直接拒绝构建, "把语言级别声明为可用却不实际使用"这类情形不再存在
- **按语言级别批量构建**: 生成脚本提供 `jdk-build <主版本>` 子命令, 从目标清单中挑出 jdk 版本首项等于该主版本的全部目标, 按清单顺序逐个依次构建(一次只构建一个, 因为语言级别是全局的); 批量开始前只检查一次当前语言级别, 不符合时直接拒绝且不触碰任何工作副本; 某个目标构建失败时继续构建其余目标, 结束后打印每个目标的成功与失败汇总, 存在失败目标时返回非 0 退出码; 没有目标匹配该主版本时提示后返回 0; 该子命令与单目标构建走同一条代码路径, 且不归集产物, 收集产物仍由 `copy` 子命令负责
- **境外依赖源**: 构建进程自身的依赖下载环境(如网络代理)属于机器特有环境, 不得写入受版本控制的配置, 也不得由生成脚本注入, 由使用者在本机自行配置, 否则表现为长时间无进展
- **构建进度可观测**: 生成脚本的标准输出在重定向到文件时默认是块缓冲, 必须显式改为行缓冲, 否则构建过程长时间看不到进度
- **缓存分区**: 各目标共享同一份依赖缓存, 但工作副本状态互相隔离; 不允许两个目标共用同一个工作副本目录

## 10. 登记与文档规范

- **目标清单**: 每个目标登记标识, 标签, MC 版本数组, 加载器名与版本数组, Gradle 版本, jdk 版本, 资源包格式号; 各 version 数组的首项为构建标准, 即编译对准的那一版, 其余元素为兼容范围; 目标标识同时是目录名与产物后缀, 不得重复维护; 差异与补丁内容不由清单登记, 而由该版本目录的 `diff-baseline.json`, `patch/` 与 `versions/.sync/` 决定
- **评估报告**: 版本兼容的取证结论, 实测结论与未取证项写入评估报告; 报告中必须区分"已按源码或产物取证"与"仅按文档推断"
- **源码取证优先**: 任何关于"某版本是否移除了某能力"的结论, 必须来自该版本真实产物的检查或该版本真实源码, 不得引用记忆或第三方文章; 已注释或已标记移除的文件是有效的移除证据, 但必须注明其原始表述
- **过时即清理**: 目标清单与项目信息文档中的版本覆盖范围, 层构成, 快捷命令必须随变更同步; 发现过时内容立即清理, 不保留"以后再说"的旧表述

## 11. 面向多加载器的扩展规则

本文的机制与加载器无关, 增加第二个加载器时按下述规则扩展, 不需要推翻现有结构:

### 11.1 差异分类

多加载器兼容的全部差异可归入三类, 必须分别处理:

| 类别 | 内容 | 复用性 |
|:---:|:---:|:---:|
| 平台接入点 | 注册入口, 事件订阅, 网络通道, 配置注册, 界面挂载点 | 各加载器各自一份, 不可复用 |
| 命名与映射 | 运行时符号命名方式, 是否需要重映射配置 | 各加载器各自一份, 可放在平台层 |
| 原版差异 | 原版自身的签名与类型变更 | 可跨加载器复用, 应独立成层 |

### 11.2 层组织建议

- 原版差异独立成层, 命名只体现版本区间, 不体现加载器
- 平台差异按加载器分组, 命名体现加载器
- 同一版本区间下的不同加载器, 应当复用同一份原版层(在各目标的 patch 目录下存放相同内容的副本), 只各自提供平台层与构建参数

### 11.3 需要预留的扩展点

- **产物命名与目标标识**: 引入第二个加载器后, 同名产物会发生冲突, 因此目标标识与产物名需要扩展出加载器维度; 该扩展必须仍满足"同源同序, 由参数推导"的要求, 且在只有一个加载器时不应产生冗余前缀
- **生成脚本的注入点**: 生成脚本的机制(复制, 叠加, 注入, 构建, 归集)与加载器无关, 但注入的具体参数项是平台特有的; 引入新加载器时应当把注入项配置化, 而不是在脚本中增加分支
- **目标清单的字段**: 平台版本区间的字段名应当体现平台而不是固定为某一个加载器的名字, 避免引入第二个加载器时出现"字段名与含义不符"
- **公共代码**: 业务逻辑与平台无关的部分必须完全位于基线, 平台侧只保留接入点; 若发现业务逻辑渗入平台层, 应先上移到基线再继续移植

### 11.4 移植时的验收口径

- 移植完成的最低口径是: 该加载器上的产物通过构建, 并通过与已有加载器同等范围的功能实测
- 移植不得改变基线行为; 若必须改变, 视为功能变更, 按功能变更流程处理, 不夹带在移植中

## 12. 硬约束

- 不得在补丁层内开发新功能
- 不得让任何目标的构建依赖人工临时改动
- 不得在未实测的情况下声称某版本已支持
- 不得凭推断写入"某版本不需要补丁"的结论, 必须以最旧版本上的真实构建为准
- 不得为通过编译而放宽全局的严格检查(例如把此前视为错误的检查降级为警告), 应改代码或改补丁层
- 不得删除或跳过区间内的实测环节
- 不得在只改产物名的情况下了事, 产物名, 目标目录名, 内部元信息声明必须三者一致
